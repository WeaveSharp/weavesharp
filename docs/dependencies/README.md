# Dependencies

WeaveSharp takes as few dependencies as it can, and every one it takes is locked, comes from a known source, is recorded and is licensed for how WeaveSharp uses it. CI enforces each rule below on every pull request.

## The rules

- **Everything is checked.** The checks read every file git does not ignore, tracked or not, so a folder escapes them only by being in `.gitignore`.
- **One source.** `NuGet.Config` clears every inherited source and fallback folder, uses nuget.org alone, maps every package id to it, and holds no other section (no `auditSources`, so advisories always come from nuget.org) and no insecure connections, so a source configured on a developer's machine or a CI runner can never supply a package. No other NuGet configuration file may exist in the repository, no MSBuild file may add package sources or fallback folders (`RestoreSources`, `RestoreAdditionalProjectSources` and their kin) or move a lock file (`NuGetLockFilePath`), no MSBuild file may import another file or name an SDK that could come from a feed, no response file (`.rsp`) may exist, `global.json` names no MSBuild SDKs, and no workflow may name a source on the command line, add one, or set one through a setup action's inputs or the environment.
- **Exact, central versions.** Versions live only in `Directory.Packages.props`, each one exact. A project's `PackageReference` names the package without a version, `VersionOverride` and `PackageDownload` are not used, and no shared `.props` or `.targets` file declares packages.
- **Lock files.** Every project restores with a lock file at its default path, and its `packages.lock.json` is committed. Lock files and central versions are turned on only in the root `Directory.Build.props` and `Directory.Packages.props`, and nothing else may turn them off. CI restores in locked mode, refuses a restore that changes a lock file or creates one that isn't committed, and every restore in CI is locked, whatever command triggers it. MSBuild files are recognized by content as well as extension: any file that parses as XML, in any encoding and after any preamble, with a `<Project>` root is a project or import, whatever its name (`.msbuildproj`, `.vcxproj` and the rest), and so is every project a solution file lists. MSBuild matches property, item, metadata and attribute names without regard to case, so the rules do too, and no MSBuild file may set a property that redirects imports (`CustomAfterMicrosoftCommonTargets`, `DirectoryBuildPropsPath`, `MSBuildExtensionsPath` and the like); and each folder holds at most one project, so its lock file is the one restore writes and CI checks.
- **Advisories.** NuGet audits direct and transitive packages on every restore. Because warnings are errors, a known advisory stops the build until the package is updated, or the advisory is suppressed with `NuGetAuditSuppress` and a recorded reason. No other `Directory.Build.props`, `Directory.Build.targets` or `Directory.Solution.*` may exist, nor any `.user` or response file, custom `Target` or `UsingTask`, change to the SDK's `Known*` items or a `FrameworkReference`'s pack versions, property that moves where restore writes (the artifacts layout included), or committed build output under `obj/` or `bin/`; and the root files set each setting exactly once, directly, with no `Choose` or `Target`. Only the root `Directory.Build.props` sets the audit (`NuGetAudit` true, `NuGetAuditMode` all, `NuGetAuditLevel` low) and `TreatWarningsAsErrors` true, unconditionally; no MSBuild value names an audit warning code (NU1900 to NU1999), read after character references are decoded; warning lists (`NoWarn`, `WarningsNotAsErrors`, `WarningsAsErrors` and the `MSBuildWarnings*` lists) hold only literal codes besides their own `$(Name)`, so no property can assemble a code; and an advisory is suppressed only there, by `NuGetAuditSuppress` with a `Reason`.
- **Licenses.** Every package's license must be in `license-policy.json`'s allowed list, or have an exception there naming the package, its version, its use, the reason and the decision that allows it. A license for code that ships in an extension is the operator's decision. Packages used only under `experiments/`, which ships nothing, have their licenses recorded but not restricted (`unrestrictedUses`); code moves from `experiments/` into the product only through SEC-05's license review.
- **npm.** `.npmrc` pins the npmjs.org registry, turns install scripts off and saves exact versions, and may not add scoped registries, credentials, proxies or certificate settings. Every `package.json` has a committed `package-lock.json` whose every package resolves from npmjs.org with a sha512 integrity. Workflows install with `npm ci --ignore-scripts` only and run no `npx`, `npm exec`, Python installer, .NET tool or downloaded script, and npm is the only JavaScript package manager. `package.json` scripts keep the same rules as workflow commands, since CI runs them by name, and npm's implicit hooks (`pre*`, `post*`, `install`, `prepare` and the rest) may not exist.
- **What restore actually does.** The rules above read files; MSBuild evaluates them. So CI also checks what restore actually does, for every project on every platform (`scripts/check-restore-graph.py`): before restoring it asks MSBuild for NuGet's restore graph, to fail fast, and after the real restores it reads the spec each restore recorded in the project's `obj/project.assets.json`, which a separate evaluation can't stand in for. It refuses any project whose effective restore differs: sources other than nuget.org, fallback folders, a packages folder inside the repository, a lock file that is missing, unlocked or moved, an audit that is off or narrower than all packages at level low, advisories suppressed anywhere but the root (with a reason), warnings not treated as errors or audit codes silenced, central versions or transitive pinning off, a dependency that isn't exact and central, and any package downloaded outside a lock file except the targeting packs the SDK fetches for an older target framework.
- **License expressions** are read with SPDX precedence: `AND` binds tighter than `OR`, parentheses group, and a license with an exception (`X WITH Y`) is allowed only when the whole `X WITH Y` is.

## The register

`register.json` lists every NuGet package any project restores and every npm package `package-lock.json` pins, direct or transitive. For each one it gives:

- its ecosystem (`nuget` or `npm`), id and exact version;
- the source it came from;
- the content hash or integrity its lock file pins;
- its license;
- each project that uses it, directly or transitively;
- how WeaveSharp uses it: `test` for `tests/`, `experiment` for `experiments/`, `development` for npm development dependencies, and `product` for everything else.

`.github/scripts/dependency-register.py` generates the register from the committed lock files: NuGet packages with the restored packages' own metadata, npm packages from `package-lock.json` alone, which must pin a sha512 integrity and an npmjs.org source for each. CI checks that it matches, and runs `npm audit` on every platform. Never edit it by hand.

## Adding or changing a dependency

1. Add or change its exact version in `Directory.Packages.props`, and reference it without a version.
2. Restore (`dotnet restore`) so the affected lock files update, and commit them.
3. Regenerate the register: `python3 .github/scripts/dependency-register.py write`.
4. Read the register's diff: every new package, direct or transitive, its source and its license. If a license isn't allowed, don't add an exception yourself; ask for a decision.
5. Run `python3 .github/scripts/check-supply-chain.py` and `python3 .github/scripts/dependency-register.py check`, and open the pull request.

Supply-chain changes are security work: the Builder reviews every dependency change, and the Reviewer reviews the rules before a release that carries them.
